# Clean billing baseline for repeat-inflation fraud — v2 review

The single fix commit (87a6944) on top of the v1 tree responds to all six v1 findings. The substantive change makes `BillingAnomalyService` build its "normal" billing range from a *clean* population: when wired with a `FraudAnalysisRepository`, a `ThresholdConfig` and a `DuplicateDetector`, it drops any historical claim that is already flagged HIGH/CRITICAL or is a near-duplicate (similarity ≥ `DUPLICATE_THRESHOLD`) of the claim under analysis before computing the mean/stddev. This directly severs the root cause behind v1 #1 (order-dependent scoring) and #2 (savings KPI collapse), which shared one mechanism — the baseline being contaminated by the fraud it was meant to catch. The remaining findings are addressed with small, scoped changes: fail-fast on a missing `APP_SECRET` outside dev (#3), dev-profile gating of demo seeding (#4), a documented TLS deferral (#5), and a new `RepeatInflationTest` regression (#6). The scoring weights and `ThresholdConfig` bands are untouched, so prior behavior on non-repeat cases is preserved.

Watch for: nothing blocking. One design note worth recording (confirmed): the clean baseline is applied in the scoring path and in the dashboard/report KPI readers, but `ClaimService` still scores each claim once at submit and never recomputes, so a claim submitted *before* a later duplicate is flagged keeps its original stored score. This no longer causes the v1 decay (the first copy is already an outlier against the clean seed baseline and stays HIGH), and the live run shows later copies scoring at or above the first — so it is a latent property, not a defect. The DTO/HTTP charge field names (`medicineCost`/`doctorCharges`/`labCharges`/`insuranceAmount`) differ from the test's `Claim`-constructor field order, but both map to the same five summed components; no behavioral gap.

**Verdict**: APPROVED

## High-level view

The baseline-contamination root cause is fixed at the right layer. `BillingAnomalyService.historicalAmounts` now takes the whole target claim and filters the per-procedure/per-provider history through an `isContaminating` check that excludes already-flagged and near-duplicate claims. Because this is the one place both the scoring engine and the KPI readers draw their baseline, fixing it once repairs both v1 #1 and #2 together. The filtering is null-safe: the original single-arg constructor passes `null` collaborators and applies no filtering, so every pre-existing test and caller keeps its old behavior.

The clean-baseline analyzer is wired into the three production entry points that need it — `FraudRiskService` (scoring), `DashboardService` (`potentialSavings`), and `ReportService` (`potentialBillingInflation`) — via a new optional 4-arg constructor, with `App.bootstrap` passing the real `FraudAnalysisRepository`. The dashboard and report services construct their own `DuplicateDetector`; the risk service reuses the one it already holds.

The security and seeding findings are closed by gating on an `APP_ENV` dev profile. A missing `APP_SECRET` now throws at startup unless the profile is dev (or unset), and demo seeding — the four known-credential accounts — only runs under the dev profile; a non-dev process logs "demo seeding disabled" and starts with empty stores. TLS stays a documented reverse-proxy deferral, consistent with the sandbox constraint.

The regression test is real: it drives three identical inflated claims through the full `ClaimService` pipeline against a clean seed baseline and asserts later copies do not score below the first, all stay HIGH/CRITICAL, billing anomaly stays non-zero on repeats, and `potentialSavings` stays positive. Neutralizing the fix makes it fail (s1=73.5, s2=64.3); restoring makes it pass.

### Clean-baseline exclusion resolves #1 and #2 at a single chokepoint

The v1 decay came from `historicalAmounts` drawing the "normal" range from the live, mutable same-procedure population minus only the claim itself, so identical inflated copies became each other's baseline. The fix changes the signature to take the whole target claim and inserts one guard inside the history loop:

```java
if (isContaminating(target, c)) {
    continue;
}
```

`isContaminating` excludes a historical claim when its stored analysis is HIGH/CRITICAL (`thresholds.isHighRisk`) or when `duplicateDetector.similarity(target, candidate) >= thresholds.getDuplicateThreshold()`. The helper methods all exist and behave as used (`ThresholdConfig.isHighRisk` matches HIGH/CRITICAL, `getDuplicateThreshold` default 0.85, `FraudAnalysisRepository.findByClaimId`, `DuplicateDetector.similarity`). Both predicates no-op when the optional collaborators are null, so the single-arg constructor path is unchanged.

Live confirmation on an open port (`PORT=18090`, dev profile), three identical $100k "Experimental Spine Fusion" claims submitted in sequence through the HTTP API:

```
ZINF-1 -> billingAnomaly 1.0  finalScore 67.0  HIGH
ZINF-2 -> billingAnomaly 1.0  finalScore 77.2  HIGH
ZINF-3 -> billingAnomaly 1.0  finalScore 77.6  HIGH
dashboard potentialSavings = 299100.00  (flagged 3, highRisk 3)
```

Later copies score at or above the first and all stay HIGH; the billing layer stays at 1.0 on every copy instead of collapsing to 0.0 on the repeats. The savings KPI is positive rather than the v1 `0.00`. The absolute figures differ from the orchestrator's quoted 67.6/76.6/77.1 / 291000 because the baseline population for this procedure differs from that run, but the behavior — no decay, non-zero billing on repeats, positive savings — matches.

### Wiring through the three KPI/scoring entry points

`FraudRiskService` gains a parallel optional constructor (`claims, patients, analyses, thresholds`); `App.bootstrap` passes the real `analyses` repo into it, and `DashboardService`/`ReportService` each build the full analyzer directly (each with its own `DuplicateDetector(claims)`). The single-arg/3-arg constructors are retained with null collaborators, which is why the 15 prior tests pass unchanged and the suite now reports 16 passed / 0 failed.

### #3 fail-fast secret and #4 seed gating

`resolveSecret` returns `APP_SECRET` when set; otherwise it falls back to the committed dev secret only under the dev profile (`APP_ENV` unset/blank/`dev`) with a stderr warning, and throws `IllegalStateException` in any other profile. Verified: `APP_ENV=prod` with no `APP_SECRET` refuses to start with that exact message. Seeding is wrapped in `if (isDevProfile())`; a non-dev start logs `Non-dev profile (APP_ENV=prod): demo seeding disabled.` and the stores are empty — a login with a former seed credential returns no session. Both gates key off the same `isDevProfile()` helper, so a single `APP_ENV` setting governs secret fallback and seeding together, which is the right coupling.

### #6 regression test genuinely exercises the fixed path

`RepeatInflationTest` seeds a stable ~$10k knee-surgery population, then submits three identical $100k claims through `ClaimService.submitClaim` (full score-and-store pipeline, same as production) with the analyses repo wired. It asserts `s2 >= s1` and `s3 >= s1` (the core regression), that all three are `isHighRisk`, that billing anomaly on the 2nd and 3rd stays `> 0`, and that `DashboardService.potentialSavings()` is strictly positive. To confirm it is meaningful rather than vacuous, I temporarily forced `isContaminating` to return `false` and reran: the test failed at the first assertion with `s1=73.5, s2=64.3` — exactly the v1 decay. Restoring the fix returned the suite to 16 passed / 0 failed, and `git status` shows the source tree clean.

### Frozen submit-time scoring (unchanged, now benign)

`ClaimService` still stores one `FraudAnalysis` per claim at submit and never recomputes. The distinction that keeps this benign: the dashboard/report readers recompute billing excess live against the clean baseline, so the savings KPI does not depend on the frozen per-claim store, and the first-in-a-cluster copy is already a clear outlier against the legitimate seed population regardless of what arrives later. Recorded as an assumption to preserve, not a defect.
