# Pure-JDK Medical Claim Fraud & Inflated-Billing Detector — v1 review

The branch is a greenfield build of the PRD v1.0 fraud detector, delivered as a dependency-free Java application because the sandbox is network-isolated (INTEGRATIONS_ONLY: Maven Central 403, every other registry 000, no artifact cache). Spring Boot, Jackson, JUnit, JDBC drivers and a Python ML service are all unreachable, so the author took the PRD's "Option B — Java-only ML" to its extreme: an HTTP/JSON micro-framework over `com.sun.net.httpserver`, in-memory `ConcurrentHashMap` repositories, PBKDF2 + HMAC-signed-token security, and a five-layer explainable fraud-scoring engine, all built with `javac`/`jar` through a committed `build.sh`. The four PRD phases are present and wired end to end (login → submit → validate → score → persist → read back → investigate → dashboard/report/notify). `./build.sh clean build` exits 0 and `./build.sh test` reports 15 passed / 0 failed; a live server on an open port passes the Phase 1–4 acceptance smoke tests. This review judges the pure-JDK implementation against the PRD's functional behavior and MVP phasing, not against the idealized stack — the stack substitution is a documented, correct response to the constraint.

Watch for: the fraud score is computed once at submission and never recomputed, which makes the engine **order-dependent** — a cluster of identical inflated claims scores the *second and later* copies LOWER than the first because the earlier copies become the "normal" billing baseline (confirmed, observed live: three identical $100k knee claims scored HIGH/MEDIUM/MEDIUM). The same baseline contamination makes the `potentialSavings` KPI read `0.00` exactly when repeat-inflation fraud is present (confirmed). The dev HMAC secret and plaintext seed passwords are safe only because they are gated behind env overrides (confirmed). None of these block the MVP, but the scoring order-dependence is the one a reviewer should weigh before shipping.

**Verdict**: APPROVED

## High-level view

The transport and persistence substitutions are clean. The micro-framework (`Router`/`HttpContext`/`Json`) and `InMemoryRepository` sit behind the same controller/service/repository seams a Spring app would use, so the deferred pieces (real DB, SPA, SMTP) are drop-in replacements rather than rewrites. The hand-written JSON codec and router are correct for the API's needs and are backed by direct round-trip and path-matching tests.

Security posture is appropriate for the constraint: PBKDF2WithHmacSHA256 with per-user salt and constant-time compare, and a hand-rolled HMAC-SHA256 stateless token with signature + expiry verification. Two items are posture notes rather than defects because they are env-overridable: the token secret defaults to a hard-coded dev string, and seed account passwords are known/plaintext in `Seed.java`. Plain HTTP (no TLS) is a documented deferral.

The scoring engine is the substantive area. Five layers (supervised logistic stub, unsupervised z-score anomaly, billing deviation, duplicate similarity, provider/patient behavior) combine with documented weights into a 0–100 score classified by a configurable `ThresholdConfig`, and the Explainable-AI risk factors are generated from real feature values. The weakness is temporal: analyses are frozen at submit time and the billing/anomaly baselines are drawn from the live claim population, so identical repeat claims erode their own signal and later duplicates score lower than the first. The duplicate-similarity layer still fires on the repeats, so they are not missed entirely, but the billing component — the PRD's headline "inflated billing" signal — collapses on exactly the repeat-inflation pattern it should catch.

Phase 4 (dashboard, search/filter with pagination, three report types, audit log, in-app notifications, provider risk) is complete and behaves per the acceptance criteria, with role gating (403/401) demonstrated on the investigation and audit endpoints. The `potentialSavings`/`potentialBillingInflation` figures inherit the baseline-contamination issue above and will under-report.

Test coverage is real: every test drives actual services over real repositories and asserts computed outputs and classification boundaries, and the harness fails the build on any assertion error. The gap is that no test exercises the order-dependent scoring path, so the engine's main behavioral weakness is invisible to the suite.

<summary>Issues (6)</summary>

1. **Order-dependent scoring** — analyses are computed once at submit and never recomputed; identical inflated claims score later copies lower than the first because earlier copies become the billing baseline. Decide whether to recompute analyses (or score against a frozen/seed-only baseline) so repeat inflation doesn't dilute its own signal.
2. **Savings KPI under-reports on repeat fraud** — `potentialSavings`/`potentialBillingInflation` use `amount − currentMean`, and the mean is inflated by the fraudulent claims themselves, driving the figure toward 0 precisely when fraud is present. Compute excess against a clean/seed baseline.
3. **Dev token secret default** — `APP_SECRET` falls back to a committed string; anyone can forge tokens if it isn't overridden. Fail fast (refuse to start) when `APP_SECRET` is unset outside dev.
4. **Plaintext seed passwords / known accounts** — `Seed.java` ships four known-credential accounts printed to stdout; ensure seeding is disabled or gated in any non-dev profile.
5. **No TLS** — server is plain HTTP; documented as deferred. Confirm a terminating proxy is assumed before any real deployment.
6. **Scoring order-dependence is untested** — the suite never submits two identical inflated claims in sequence, so the baseline-contamination behavior is uncovered. Add a regression test asserting repeat inflated claims do not score below the first.

### Transport and persistence substitution

One literal-vs-template routing hazard is handled deliberately: `/api/claims/high-risk` and `/api/claims/{id}/analysis` are registered (via `InvestigationController`) *before* `ClaimController`'s `/api/claims/{id}`, and `ReportController`'s literal `/api/reports/fraud-analytics` before its templated routes, so the literal wins. This ordering is load-bearing — the router matches in registration order with no specificity ranking, so adding a new `/api/claims/...` literal route after `ClaimController` would silently be shadowed by the `{id}` template. It is called out in `App.bootstrap` comments; preserve the order.

### Security posture

Two posture notes, both env-gated so neither is a defect in isolation. `App.resolveSecret()` returns a committed `fraud-detector-dev-secret-change-me` when `APP_SECRET` is unset — anyone who knows it can mint valid tokens for any role, so a real deployment must set it; refusing to boot without it outside dev would be safer (confirmed). `Seed.java` creates four fixed accounts with known passwords and prints them to stdout (confirmed); fine for the sandbox demo, but seeding must be gated off in any non-dev profile. Plain HTTP is a documented deferral (TLS at a proxy).

### Five-layer scoring engine and the order-dependence

The engine combines fraud 0.30 / billing 0.25 / duplicate 0.20 / provider 0.15 / patient 0.10 into a 0–100 score, and the behavioral weakness is temporal — confirmed, not theoretical. `ClaimService.submitClaim` scores a claim once after persistence and stores the `FraudAnalysis`; it is never recomputed. `BillingAnomalyService.historicalAmounts` draws the "normal" range from the *current* same-procedure population (excluding only the claim itself). So when identical inflated claims arrive in sequence:

```
submit CLM-A ($100k knee, no knee history)  -> billingAnomaly 1.00 -> finalScore 63.3 HIGH
submit CLM-B (identical to CLM-A)            -> billingAnomaly 0.00 -> finalScore 52.2 MEDIUM
submit CLM-C (identical to CLM-A/B)          -> billingAnomaly 0.00 -> finalScore 52.6 MEDIUM
```

By the time CLM-B is scored, the knee-surgery history is `[100000]` (then `[100000,100000]`), so the mean is the inflated amount, the z-score is ~0, and the billing layer — the PRD's primary inflated-billing signal — reports no anomaly. The duplicate layer still fires (similarity 1.0), which keeps the repeats at MEDIUM rather than LOW, so they are not fully missed; but a coordinated repeat-inflation scheme ends up with its later claims scored *below* the first and absent from the HIGH/CRITICAL list and the investigator notifications. Two mitigations are reasonable: recompute stored analyses when the population changes, or score billing against a frozen/seed-derived baseline rather than the live mutable population. (confirmed)

### Phase 4 analytics and the savings KPIs

`potentialSavings` (dashboard) and `potentialBillingInflation` (fraud-analytics) sum `amount − historicalMean` over flagged claims. Because `historicalMean` is the live population mean — contaminated by the inflated claims themselves — the excess trends to 0 for exactly the repeat-inflation case, and was observed as `0.00` live in a run where a HIGH claim existed. The figure is only meaningful when a flagged claim is an outlier against an otherwise-clean history; under repeat inflation it under-reports. Same fix as the scoring issue: compute excess against a clean/seed baseline. (confirmed) The rest of Phase 4 (filters/pagination, three report types, ADMIN-only audit, investigator-targeted notifications, provider `fraudRate = flagged/total`) matched the acceptance criteria under live calls.

### Validation and claim lifecycle

`SubmitClaimRequest.fromJson` raises 400 on a malformed number or non-ISO date *before* `ValidationService` runs, so a bad `admissionDate` string surfaces as a parse error rather than reaching the FR-03 date-order check — worth knowing when interpreting 400 messages. The FR-03 rules themselves (required fields, non-negative charges, total = sum of components by `BigDecimal.compareTo`, discharge-not-before-admission, referenced patient/provider exist, duplicate `claimId` → 409 ahead of the 400 batch) were confirmed live: 201 valid, 400 with the date-naming message, 409 duplicate, 401 no-token, 404 unknown.

### Test coverage

The one meaningful coverage gap is the untested order-dependence: no test submits two identical inflated claims in sequence, so the baseline-contamination behavior that drops later duplicates to MEDIUM is invisible to the suite. `FraudRiskServiceTest`'s inflated+duplicate case passes only because its fixture seeds a stable ~$50k normal population alongside the duplicate, keeping the billing z-score high — it does not reproduce the submit-order path. A regression test asserting repeat inflated claims do not score below the first would lock in whichever fix is chosen. Otherwise the harness is a real signal (assertions throw → non-zero exit → `build.sh` fails the build) and the tests assert computed values and classification boundaries over real repositories rather than static constants.
